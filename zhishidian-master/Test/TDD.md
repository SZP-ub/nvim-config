# Unity 测试框架下 C 语言 TDD 流程与文件结构笔记整理

## 1. TDD 流程简介

TDD（测试驱动开发）是一种围绕**测试和实现**反复循环的开发流程。其核心步骤为：

1. **编写测试**（Red/红灯）：先写测试用例，测试未通过，说明功能未实现或实现有误。
2. **编写实现**（Green/绿灯）：补充实现代码，使测试通过。
3. **重构**（可选）：优化代码结构，保证测试依旧通过。
4. **添加新功能**：重复上述流程。

---

## 2. 红灯与绿灯阶段说明

- **红灯（Red）**：测试未通过。此时通常只写了测试文件，函数未实现或实现错误。
- **绿灯（Green）**：测试通过。此时已经补充了实现文件，测试可以成功运行。

---

## 3. 文件归属与目录结构建议

- **实现代码**：放在 `src/` 目录（如 `src/add.c`、`src/add.h`）。
- **测试代码**：放在 `test/` 目录（如 `test/test_add.c`）。
- **测试框架**：如 Unity 源码放在 `unity/` 目录。

### 推荐目录结构

```
project-root/
├── src/         # 实现代码
│   ├── add.c
│   └── add.h
├── test/        # 测试代码
│   └── test_add.c
└── unity/       # Unity 测试框架代码
    └── unity.c
```

---

## 4. TDD 实践流程举例（以 `add()` 为例）

### 4.1 第一步：编写测试文件（红灯阶段）

```c
// test/test_add.c
#include "unity.h"
#include "add.h"

void setUp(void) {}
void tearDown(void) {}

void test_add_two_and_three_should_return_five(void) {
    TEST_ASSERT_EQUAL_INT(5, add(2, 3));
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_add_two_and_three_should_return_five);
    return UNITY_END();
}
```

- 这里只声明了 `add` 函数，实际实现还没有写。
- 运行测试会**失败**（红灯），因为还没有函数实现。

### 4.2 第二步：实现代码（绿灯阶段）

```c
// src/add.c
int add(int a, int b) {
    return a + b;
}
```

- 补充函数实现，让测试通过。

### 4.3 头文件

```c
// src/add.h
#ifndef ADD_H
#define ADD_H

int add(int a, int b);

#endif
```

- 声明函数，供测试调用。

## 5. 编译与运行

假定 Unity 源码在项目目录下（如 `unity.c`），编译命令示例：

```sh
gcc test/test_add.c src/add.c unity/unity.c -Iunity -Isrc -o test_add
./test_add
```

- **红灯阶段**：测试用例未通过（因为没实现）。
- **绿灯阶段**：测试用例通过（因为已实现）。

---

## 6. TDD 的具体循环流程

1. **写测试 test/test_add.c**  
   例如：`TEST_ASSERT_EQUAL_INT(5, add(2, 3));`
    - 编译运行，红灯（失败）。

2. **写实现 src/add.c**
    - 编译运行，绿灯（通过）。

3. **写新测试 test/test_add.c**
   例如：`TEST_ASSERT_EQUAL_INT(7, add(3, 4));`
    - 编译运行，红灯（失败）。

4. **完善实现 src/add.c**
    - 编译运行，绿灯（通过）。

5. **重复以上流程，直到功能完整、测试全部通过。**

---

## 7. TDD 在需求不明确时的作用

### 7.1 通过测试推动需求细化和设计

- 先和产品、用户或团队讨论需求。
- 尝试写第一个测试（哪怕是不完整的），如“需要一个函数，能完成什么功能”。
- 写测试过程中，会发现需要哪些输入、输出，这就是接口的原型。
- 如果参数类型不确定，可以假设一个类型，写下第一个测试，作为讨论起点。

### 7.2 测试就是需求的最小表达

- 测试内容决定接口和返回值。
- 测试失败，说明需求不清楚或接口不合理。
- 不断调整测试内容，直到大家都满意。

### 7.3 接口演化过程

- 最初只知道“需要一个加法功能”，但具体形式未知。
- 可以先写测试假设为 `add(int a, int b)`，返回 `int`。
- 后续如需支持浮点数，写 `add(double a, double b)` 的测试，推动接口变化。
- 需要支持多参数、数组或返回错误码时，测试推动接口和实现不断演化。

#### 示例：接口不确定时的 TDD 流程

1. **写最简单的测试（假设接口）**

    ```c
    TEST_ASSERT_EQUAL_INT(5, add(2, 3));
    ```

2. **实现代码让测试通过**  
   如果接口有异议，先改测试再实现。

3. **新需求出现，测试推动接口变化**  
   例如需要支持浮点数：

    ```c
    TEST_ASSERT_EQUAL_DOUBLE(5.5, add(2.5, 3.0));
    ```

4. **反复调整测试和实现，最终确定接口和功能**

---

## 8. 总结

- TDD 步骤不是简单的“编译运行”，而是**测试→实现→编译运行（反复循环）**。
- 每次增加/修改功能，都**先写测试**，再写代码，让测试通过。
- 测试放在 `test/`，实现放在 `src/`。
- TDD 不要求一开始就有完美的接口设计，测试内容是对需求和接口的最好假设，测试推动接口和实现逐步清晰，最终形成大家认可的功能。

---

这是 TDD 的核心思想之一：**通过测试驱动接口设计**。你可以按照以下步骤逐步确定结构体、函数指针、参数和返回值：

---

### 1. 明确需求，写出第一个测试

例如，你需要一个排序器能生成数组并排序。先写一个最简单的测试：

```c
void test_create_should_fill_array(void) {
    int arr[5] = {0};
    Sorter sorter;
    init_sorter(&sorter, arr, 5);

    sorter.create(sorter.arr, sorter.len);
    // 断言：数组不全为0
}
```

此时你只确定了 `create` 的参数和返回值（无返回值，参数为数组和长度）。

---

### 2. 编译，发现缺少接口或参数不合理

编译时如果报错，比如 `Sorter` 没有 `create`，或者参数类型不对，你就去头文件补充声明，保证测试能编译通过。

---

### 3. 继续添加测试，驱动接口完善

比如你需要打印数组：

```c
void test_print_should_output_array(void) {
    int arr[5] = {1,2,3,4,5};
    Sorter sorter;
    init_sorter(&sorter, arr, 5);

    // 这里你希望 print 能输出到某个地方
    sorter.print(sorter.arr, sorter.len);
    // 断言输出内容
}
```

如果你发现需要返回值或其他参数（比如输出到文件），就在测试里体现出来，然后再去接口里补充。

---

### 4. 通过不断完善测试，逐步确定接口

每次写测试时，遇到不确定的参数或返回值，就先假设一个最简单的形式，写完测试后再去实现。  
如果发现测试写起来不方便，说明接口设计可以调整，直接在测试里改，再同步到头文件和实现。

---

### 5. 只通过测试文件确定接口

**你的接口和参数设计，完全由测试驱动。**  
测试怎么用，接口就怎么设计。  
测试需要什么功能、什么参数、什么返回值，就在接口里加什么。

---

**总结：**

- 先写测试，遇到接口不确定就假设一个最简单的；
- 测试编译不过就补充声明；
- 测试写起来不方便就调整接口；
- 所有接口和参数都由测试驱动确定。

这样你就可以一步一步地通过测试文件确定结构体和函数指针的形式。
